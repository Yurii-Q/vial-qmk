# Почему при обновлении экрана терялись нажатия

Разбор проблемы «пока экран перерисовывается, клавиатура глотает клавиши» и того,
что сделано в этой прошивке, чтобы ввод не зависел от рендера.

## Симптом

При быстрой печати пропадают отдельные символы. Заметнее всего в двух случаях:

- на экране идёт активная перерисовка (анимация, календарь с ПК, вспышка алерта);
- нажатие включает слой, из-за чего включается экран `keymap` и начинается
  полнокадровый перелив.

Клавиши при этом не «залипают»: пропадает именно само нажатие, причём чаще на
той половине, где в этот момент что-то рисуется.

## Корень проблемы

Экран подключён по SPI (ST7789) и рисуется через Quantum Painter + LVGL.
Передача кадра — это блокирующий цикл по полосам: `qp_viewport` → `qp_pixdata`
→ `qp_flush`. Пока идёт передача полосы, главный цикл не возвращается, а значит
не вызывается `keyboard_task()`: матрица не сканируется, USB-очередь не
обслуживается, debounce не тикает.

В `keyboards/ergohaven/sm62/rules.mk` это зафиксировано прямым текстом:

```make
# The full-screen Orbit SPI transfer pauses matrix scanning. Accept a press
# on its first observed scan; debounce the release independently per key.
DEBOUNCE_TYPE = asym_eager_defer_pk
```

`asym_eager_defer_pk` лечит только часть случаев: нажатие, которое **попало
в скан после** передачи, засчитывается сразу, не дожидаясь устойчивого
состояния. Но если нажатие и отпускание целиком уложились внутрь блокирующей
передачи полосы, сканер не увидел ни одного из двух фронтов — событие теряется
безвозвратно. Один полный кадр 240×280 по SPI занимает миллисекунды, при
анимации полос кадры идут подряд, и окно потерь становится заметным.

## Что уже было в репозитории

В `keyboards/ergohaven/sm62/display_input.c` лежала готовая точка входа:

```c
void protocol_keyboard_task(void) {
    if (sm62_input_running) return;
    sm62_input_running = true;
    keyboard_task();
    sm62_input_running = false;
    sm62_input_initialized = true;
}

void qp_lvgl_flush_input_service(void) {
    if (!sm62_input_initialized || sm62_input_running) return;
    protocol_keyboard_task();
}
```

Функция `qp_lvgl_flush_input_service()` не вызывалась ниоткуда — поиск по
репозиторию давал единственное вхождение (её определение). То есть обслуживание
ввода во время перелива было спроектировано, но не подключено.

## Решение

### 1. Хук в общем слое Quantum Painter

`quantum/painter/lvgl/qp_lvgl.c:38` — слабая функция, которую может
переопределить клавиатура:

```c
__attribute__((weak)) void qp_lvgl_flush_input_service(void) {}
```

`quantum/painter/lvgl/qp_lvgl.c:46` — вызов сразу после `qp_flush()`, то есть
после того, как очередная полоса ушла в панель, но до того, как LVGL начал
готовить следующую:

```c
qp_flush(selected_display);
qp_lvgl_flush_input_service();
if (lv_disp_flush_is_last(disp)) {
    display_frame_completed();
}
```

Слабая функция + переопределение на уровне клавиатуры означают, что остальные
платы ничего не теряют: у них хук остаётся пустым и превращается в no-op.

### 2. Реализация на стороне SM62

`keyboards/ergohaven/sm62/display_input.c:19-26` — `qp_lvgl_flush_input_service()`
вызывает `protocol_keyboard_task()`, который прогоняет обычный `keyboard_task()`.

Защиты, без которых это опасно:

- `sm62_input_running` — защита от рекурсии: `keyboard_task()` может привести
  к новой отрисовке, а та — к новому флашу;
- `sm62_input_initialized` — до первого обычного прохода главного цикла хук
  молчит, иначе инициализационные перерисовки дёргали бы неготовый ввод;
- в `SM62_DUALCORE_RENDER` хук выходит сразу: рендер-ядро не имеет права
  входить в keyboard/TD/USB/split.

Заголовок файла фиксирует правило: `keyboard_task()` из хука — тот же владелец,
что и в главном цикле, никакого протокола, HID, housekeep или painter внутри.

### 3. Экран keymap не включается на базовом слое

`keyboards/ergohaven/sm62/display_modes.c:149` и `:153`:

```c
if (((settings->keymap_enabled && layer_state != 0) || settings->mode == 3) &&
    (local_change || local_hold || sm62_keymap_visual_active() || frame_hold)) {
```

Раньше оверлей мог включиться на любое движение матрицы, в том числе на
обычную печать в базовом слое: каждое нажатие запускало полнокадровый перелив
и создавало окно потерь. Теперь условие требует ненулевого `layer_state`,
поэтому повседневная печать вообще не трогает экран. `frame_hold`
(`display_modes.c:147-148`) удерживает keymap ещё 32 мс после кадра, чтобы
нажатие и отпускание между двумя кадрами не мигали экраном.

## Почему не наоборот

Можно было бы ускорять SPI, резать кадры или отдавать рендер на второе ядро.
Все эти варианты либо меняют картинку, либо требуют переписывать Quantum
Painter. Обслуживание ввода между полосами дешевле: оно не меняет ни кадр,
ни драйвер, и работает для любого экрана, включая `keymap`, `player` и наш
`dash`.

## Проверка

Стресс-тест: непрерывный ввод на обеих половинах, при этом хост гоняет полные
кадры дашборда (длинный текст на 12 строк, полосы, мигание) каждые 2 секунды.

- До исправления: на правой половине (её образ был собран без хука) регулярно
  пропадали символы при быстром вводе; на левой — заметно реже.
- После: 24 полных кадра, 3028 пакетов, 0 ошибок разбора и ни одного
  потерянного символа. Остаётся штатная задержка отрисовки — экран не
  успевает за каждым кадром, но ввод полный.

Обе половины должны быть прошиты одним и тем же образом: хук живёт в общей
части, но половинная логика (`display_input.c`) собирается для каждой стороны.

## Что важно помнить при доработке

- Новые опкоды протокола дашборда, меняющие железо (инверсия панели, смена
  драйвера), нельзя выполнять прямо из обработчика raw HID: это дедлок с идущим
  SPI-флешем. Такие действия складываются в очередь и применяются в `housekeep`.
- Внутри `qp_lvgl_flush_input_service()` нельзя звать ничего, что само может
  запустить флаш, кроме `keyboard_task()`, и нельзя убирать проверку
  `sm62_input_running`.
- Если появится второй потребитель хука (например, энкодер), он должен жить
  в том же `protocol_keyboard_task()`, а не добавлять второй вызов
  `keyboard_task()`.
